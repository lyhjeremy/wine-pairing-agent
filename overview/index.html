Wine Pairing Agent
Reasons about the dish, then retrieves

A LangGraph agent with retrieval as a tool

Name a dish. It works out the wine style, then finds bottles that fit it.

With its critique rewritten as a seven-point rubric, the agent passed its own review on all 10 frozen dishes (9 on the first draft) and its first pick was an accepted grape on 10 of 10. Searching the reviews with the dish text alone managed 3 of 10. A pairing now costs $0.49 at API prices and takes 34 seconds, down from $1.25 and 78 seconds when the old critique rejected every draft it saw.

The agent reasons from the dish to a wine style, searches the Wine Enthusiast review index through a LangChain StructuredTool with the budget as a filter, recommends with citations, and sends itself back when its critique finds a problem.

The upgrade, 2026-11-13

A critic with a rubric, and a pass decided in code

On the same 10 first drafts, the old free-form critique passed none and the rubric passed 9. The old prompt asked "is this a genuinely good pairing?" and passed a draft only if the reply listed no issues. It judged 2017-era reviews as of 2026 and found every wine too old, which no retry can fix. The rubric splits the judgment into seven named criteria:

Checked in code
grounded (every [n] points at a retrieved bottle), within_budget, enough_candidates
Graded by the LLM
body_match, structure_logic (acid, tannin and sweetness against fat, spice and salt), flavor_link, claims_supported (what the note says about a wine is in its review)
Out of scope
Vintage age, drinking windows, current prices and availability (the index is a fixed snapshot), and preferring another grape when the chosen one already fits
Validation
The reply must match a pydantic schema: one {"pass", "reason"} object per criterion, no extra keys. An invalid reply gets one repair attempt with the error attached; a second failure fails the critique. The overall pass is computed in src/rubric.py, never taken from the model

Does it pass everything now?

A critic that never fails is as useless as one that never passes, so I checked it three ways. Six mismatched drafts, each one dish's recommendation handed in as the pairing for a dish it clearly does not suit (the ribeye's Cabernets for the oysters, the chocolate's fortified Maury for the green curry), were all rejected: body_match, structure_logic and flavor_link failed in all 6. Rerunning the Opus critic on the 10 first drafts gave the same verdict 10 of 10 times and the same call on 40 of 40 criteria. Error analysis

Where the critics disagree

All four disagreements with Sonnet are on one criterion, claims_supported, or on the schema. Reading the drafts, Sonnet is right at least once that Opus missed:

Draft and what Sonnet saidOpusSonnet
Goat cheese salad: an invented preferencepassfail The draft says the Easton Sauvignon Blanc is "the closest to the Sancerre style you're after". Nobody asked for Sancerre: that was the agent's own target style from strategize, restated as the guest's wish. Sonnet: "the 'Sancerre style you're after' is an invented premise." The old prompt caught it too. This is a bug in the recommend prompt, which passes the target style without saying whose it is; the pizza draft does the same ("the closest match to what you're after").
Salmon: a style claim not in the reviewpassfail "The review for Stephen Ross never mentions Chablis, so calling it 'closest to a Chablis style' is invented."
Pizza: grape and tannin detailspassfail "Sangiovese is not in the Chianti review, which says only Red Blend." True of the review, though Chianti Rufina is Sangiovese-based by law, so this one is a judgment call.
Lamb: no valid verdictpassinvalid Sonnet's reply failed the schema twice, so the code counted the critique as failed. Sonnet needed the repair step on 6 of its 10 verdicts; Opus needed it on none of its 11.

The one draft the Opus critic itself failed shows the loop doing its job. For the chocolate torte, round one recommended the Mas Amiel Maury and said ten years of aging "has softened the tannins". The critic failed claims_supported: "The review calls the Mas Amiel palate 'gripping', but the pick says aging has softened its tannins." strategize took that as feedback, searched for Late Bottled Vintage Port, and round two passed with the Taylor Fladgate 2007 LBV, $18. Opus on its rerun and Sonnet both failed the same round-one draft.

The problem

A dish is not a search query

The sibling project, Wine Sommelier RAG, answers requests that already contain their search terms: "a bold red under $25" is close to a query. "Grilled ribeye with peppercorn sauce" says nothing about tannin or dark fruit, so a retriever has nothing to match on.

This agent reasons about the dish first, picks a target style from a short list of pairing principles in src/pairing.py (acid cuts fat, tannin binds protein, match weight, sweetness tames heat, regional dishes with regional wines), writes a search query for that style, and only then calls retrieval. Afterwards it checks its own answer.

Diagnosis, 2026-11-05

Why the old critique rejected every draft

The critique node passes a pairing only when its LLM review lists no issues. In the 4 scored runs it listed issues in all 12 rounds, so every run went parse, then three rounds of strategize, retrieve, recommend and critique, and stopped at the attempt limit with the issues still open. Grouping the first issue of each round, and every issue in each run's last critique (eval/critique_issues.json, coded in a review session on 2026-11-05 by a model, not a person):

Kind of issueFirst, of 12Last, of 19
The vintage is too old to trust the note76 "The 2007 JD will be about 19 years old in 2026. Its tannins have probably softened since release." (ribeye)
Quibble with one line of the explanation28 "'Searingly tart' wine next to a red wine vinegar mignonette risks stacking acid on acid." (oysters)
A different grape or weight would suit better24 "A Spätlese or a fuller off-dry Riesling would match the weight better." (green curry)
Asked for a style the index can't supply11 "The user asked for Nebbiolo and a recent vintage. Neither request is met." (risotto)

The age complaint can't be fixed by retrying. No vintage in the review file is newer than 2017, the newest of the 24 retrieved bottles was 2016, and after the first rejection strategize starts asking for "a recent vintage", which sends the search after wines the index does not have. The critique prompt has no notion that the index is a snapshot, and no rule says which issues are worth a retry. The July recorded run above passed on its first critique; on 2026-11-05 none did. That finding is what the rubric above was written to fix.

Second judge
Sonnet 5.5: $0.13 median and 9.7 s per verdict, including the repair calls it needed on 6 of 10 drafts
Retrieval
Local, no LLM call: about 0.5 s warm, 7.9 s on the first dish while the embedding model and Chroma load

Most of the saving is the retry loop now exiting: 4 calls where 10 were made. The CLI's context on every call is still most of each call's cost.

Observability

Every scored run is saved as a trace

eval/run_critic_eval.py streams the graph node by node and writes one JSON file per dish to eval/traces/: each node's start and duration, every LLM call's model, cost, duration and token counts, the search_wines tool call with its arguments and the six bottles it returned, and the critique JSON. The replay above reads those files directly. For ad hoc runs, python -m src.cli "..." --trace still prints a timed tree and saves it under traces/.

Limitations

Ten dishes, a key I wrote, and no human labels

The set is 10 dishes, scored against an answer key of accepted grapes that I wrote from standard pairing rules. Pairing has few single right answers, so a grape match is a floor; no sommelier or blind tasting checked the picks. The critic is Opus grading Opus's own drafts, which can favor its own reasoning, and the Sonnet judge that disagreed on 4 of 10 is itself only another model. No person has labeled any draft; eval/critic/labeling_sheet.csv has the 40 criterion calls laid out for one.

The six mismatched controls were added after the main run had passed 10 of 10, to test whether the critic passes everything, so they were not part of the frozen protocol. Sonnet's replies needed the repair step on 6 of 10 drafts and failed it once; the run did not save those raw replies, so why they failed validation is not recorded (the script saves them now). Retrieval filters on price only, and the index holds the 30,000 highest-scored reviews, all from 2017 or earlier.

Next

What I would do next

  • Have a person fill in eval/critic/labeling_sheet.csv and measure both judges against it, starting with claims_supported, the one criterion they split on.
  • Turn claims_supported into a code check where possible: match each quoted descriptor against the cited review text before asking a model.
  • Add a color and grape filter to the search tool, so a "red" target style cannot retrieve whites.
  • Grow the dish set past 10 with dishes the key handles badly (spicy and sweet, vegetarian, fortified wines), and freeze the controls as part of it.
  • Measure the API backend, which skips the CLI's context and should cut the $0.12 per call.

How it was built

Stack

Agent
LangGraph StateGraph with five nodes and a conditional retry edge (src/graph.py)
Tool
src/tools.py wraps retrieval as a LangChain StructuredTool with a typed schema
Index
Wine Enthusiast reviews embedded with sentence-transformers and stored in Chroma; 30,000 by default, --all for the full 129,971
Generation
Claude through the Claude CLI by default; ANTHROPIC_API_KEY switches to the API
Critique
src/rubric.py: three code checks and four LLM criteria in a pydantic schema, one repair attempt, pass decided in code
Tracing
src/trace.py for the CLI; eval/run_critic_eval.py writes the replayable traces in eval/traces/
